## 动手前的事实核查(这是选型的依据)

磁盘实况:`data/logs/app.log` **3.2 MB**、内容跨 **2026-07-24 ~ 2026-09-29(26 个使用日)**、32,479 行、**零个备份文件**。

逐日统计(从真实文件量出):

| 指标 | 值 |
|---|---|
| 平均单日 | 100 KB |
| 最大单日(2026-09-28) | 686 KB |
| 5 MB 阈值下最大单日占比 | 13.4% |

**结论:问题不是"单个文件写太大",而是"一个文件跨了两个月"。** 原有的 `RotatingFileHandler(5MB×3)` 在当前强度下要 26 天才轮转一次,等于没轮。

### 隔离验证:现有 `app.log` 不被破坏

在临时文件上预置"历史内容"再挂新 handler 写入:

| 检查 | 结果 |
|---|---|
| 原有内容是否保留 | **是** |
| 新日志是否追加 | **是** |
| 行数 前/后 | 2 / 3 |

`TimedRotatingFileHandler` 以追加方式打开已存在的文件,不会截断。所以那份跨两个月的 `app.log` 会原样保留,直到首次轮转时被改名为 `app.log.<轮转日>`。

## 待重启后手工验证(需你操作)

**前置**:重启服务(后端 `logs.py` 改了,不会热加载)+ 强刷浏览器(前端重建)。

> 这些步骤在本环境**做不了**:本机正有一个服务进程(PID 21008,09:15 启动)持有
> `data/logs/app.log`,Windows 下无法改名被占用的文件。

| # | 步骤 | 期望 |
|---|---|---|
| 1 | 重启后看 `data/logs/app.log` | 仍存在,且原有内容未被清空 |
| 2 | 触发一次轮转 | 生成 `app.log.<日期>`;`app.log` 重新开始 |
| 3 | 打开前端「运行日志」面板 | 能看到重启后的新日志(实时推送正常) |
| 4 | 面板开着时提交一个小任务 | 日志实时追加、无卡顿 |
| 5 | 确认提示文案 | 已变为"在后端目录 data/logs/ 查看完整日志(按日期分文件)" |

第 2 步的触发方式(脚本):

```bash
.venv/Scripts/python.exe -c "
from backend.core.logs import logger
for h in logger.handlers:
    if hasattr(h, 'doRollover'):
        h.doRollover(); print('已手动触发轮转')
"
ls -la data/logs/
```

> 注意:这条命令需在**服务停止**时运行 —— 服务运行时该文件被占用,轮转会失败。
> 验完把轮转出的 `app.log.<日期>` 与新的 `app.log` 合并回原状,或自行清理。

## 执行期发现并修正的三处(原计划的问题)

1. **护栏不该操作真实的 `data/logs/app.log`**。原计划用它验证解耦,实测发现:
   ① 运行中的服务进程持有该文件句柄,Windows 下改名抛 `PermissionError [WinError 32]`;
   ② 测试会往用户真实日志写标记、还会轮转它。
   **改为临时文件 + 临时 handler** —— 验的仍是"面板不依赖文件内容"。
   (另:`shutil.move` 的降级路径会先复制成功、再 unlink 失败,留下残留副本,实测确认。)

2. **标准库把 `when` 存成大写**(`'MIDNIGHT'`),原断言 `== 'midnight'` 必然失败。
   改为比较 `.lower()`。

3. **补一条"轮转确实发生"的前置断言**。原计划只断言"轮转后面板仍可见" ——
   若 `doRollover()` 空转,这条会**真空通过**,测不到任何东西。
   现已先断言轮转产物存在(列出目录内容作为失败信息)。
