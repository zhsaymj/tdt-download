## 2. 隔离效果（核心指标）

**目的**:验证改造要解决的那个问题 —— 任务运行期间 Web 接口是否仍然响应。

**方法**:启动服务，提交真实任务（1600 张缓存瓦片拼接，含 `build_overviews` —— 改造前
8.3 秒停顿的来源），任务运行期间每 0.2s 请求一次 `/api/tasks`，采样 50 秒。

| 指标 | 改造前（实测） | 改造后（实测） |
|---|---|---|
| 采样样本 | — | 123 个（期间确认有 running 任务） |
| P50 | — | **181 ms** |
| P99 | — | **241 ms** |
| 最慢 | **8452 ms**（完全无响应） | **243 ms** |

**结论:最慢响应从 8.4 秒降到 243 毫秒，约 35 倍改善。** 验收标准（P99 < 1s 且最慢 < 3s）通过。

## 3. 端到端功能验证

### 3.1 完整链路

提交 → Scheduler 派发 → worker 子进程执行 → 拼接 → 落库 → 前端可见。

```
任务 verify_isolation_e2e：total=1722（含复用已缓存瓦片）
结果 status=done  message=完成:1722 张成功,0 张失败
stages: download=done, geotiff=done
```

### 3.2 暂停（改造前完全失效的功能）

**背景**:改造第一版的控制循环与任务执行同线程，`run_until_complete` 阻塞导致
`pause` 消息一直躺在队列里 —— 实测「发 pause 后 3 秒，任务仍跑完全程」。
修复方式:信号接收独立成 `_SignalConsumer` 线程 + 每 worker 双队列。

**测试**:提交需**真实下载**的任务（上海附近，未缓存，4136 张），下载进行到 325/4136 时点暂停。

```
第1次轮询: paused | downloaded=963/4136 | 已暂停(963/4136)
```

**结论:下载中途暂停生效**（963 张时停住）。

> 首次尝试用全缓存范围测暂停，因下载阶段瞬时完成而未能验证 —— 该测试必须用未缓存范围。

### 3.3 续跑（断点续传）

暂停于 963/4136 后调 `resume`：状态转 `running`，`downloaded` 从 963 继续增长至 1356。
已缓存瓦片未重下，断点续传正常。

### 3.4 取消

`DELETE /api/tasks/{id}` 走 `request_cancel` 路径,任务删除成功,**worker 进程未受影响**
（日志无 worker 异常）。

### 3.5 干净退出

直接验证 `Scheduler.shutdown()`:

```
启动后: 1 个 worker, is_alive=[True], active_children = 1
shutdown() 耗时 0.10s
shutdown 后 is_alive = [False], active_children = 0
```

**结论:worker 干净收工，0.10 秒，无残留进程。**

> 说明:首次测试时用 `Stop-Process -Force` 强杀服务进程，留下了一个孤儿 worker。
> 原因是 Windows 上 `daemon=True` 标志**不跨进程生效** —— 父进程被强杀时子进程不会自动终止。
> 这是**强杀父进程**的固有行为，不是代码缺陷；正常退出路径（lifespan → `await shutdown()`）完全干净。
> 同类情形在 `start.bat` + Ctrl-C 的日常用法下不会发生。

## 9. 多 worker 引入的竞态（已修复）

放开多 worker 后暴露了一个**单 worker 时不可能出现**的缺陷：

**瓦片缓存非原子写**。`downloader.py` 用 `path.write_bytes(data)` 直接写缓存，
而命中判定是 `exists() && size > 0`。缓存路径只由 `provider.key + z + col + row`
决定、**与任务无关** —— 两个范围重叠的任务会写同一路径，于是：

- 进程 A 写了一半时，进程 B 判定「命中」，把**残缺瓦片**带进拼接（产出错像素/nodata）
- 且该文件此后永远命中跳过分支，**不会自愈**

**实证**（模拟非原子写 + 复刻命中判定）：

```
B 判定缓存命中 = True  (当时 50004 字节)  最终 100004 字节
★竞态确认★ 残缺瓦片(50004/100004)被当成有效缓存,且不会自愈
```

范围重叠是常见情形（相邻范围的两个任务、重跑失败任务同时开小任务、
同区先跑影像再跑注记）。

**已修复**（提交 `7dd38cc`）：改为「同目录临时文件 + `os.replace` 原子改名」，
并把 `OSError` 纳入重试列表（Windows 上 `os.replace` 可能因文件句柄争抢抛
`PermissionError`，这正是多 worker 下的常态，不该让单张瓦片中止整个任务）。

**历史缓存审计**：用 rasterio 抽样 633 个缓存瓦片（img/cia/vec/ter），**零损坏**。
合理 —— 该竞态只在多 worker 下产生，而多 worker 是本次才放开的。
