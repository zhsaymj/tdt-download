## 实现期发现并修复的 bug(不在原计划内)

### 级别范围有两处判定,且互相矛盾 —— Google z21 / Esri z19 实际下不到

`api/tasks.py` 按数据源的 `max_zoom` 判定级别上限(Google 21 / Esri 19),
而 `models.py::level_list` 对所有非 DEM 源**硬编码 18**。`create_task` 走的是后者:

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `google_img` `[17,18,19]` | `[17,18]` | `[17,18,19]` |
| `google_img` `[20,21]` | **`[]`**(任务建不出来) | `[20,21]` |
| `esri_imagery` `[18,19]` | `[18]`(静默丢 19) | `[18,19]` |

**后果**:上一轮 PR 的核心能力"Google 开到 z21"实际不可用;用户把 Esri 从 z18
提到 z19 的决定也一直没生效。此前测试全绿,是因为所有真实下载验证都只用了
≤18 的级别。

**修法**:新增 `core.formats.z_cap_of / z_floor_of` 作为级别范围的唯一判定处,
`models.level_list` 与 `api/tasks._z_cap_for` 都委托给它。回归护栏含一条
"逻辑里不得再有字面量 18"(剥掉 docstring 与注释后检查 —— 文档里写
"天地图 1-18"是正常的)。

> 这条 bug 是 **z18 裁剪验收暴露出来的**:不修的话 z19 根本不会被请求,
> 验收本身是空转的。
