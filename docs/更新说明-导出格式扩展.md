# 更新说明 · 导出格式扩展

> 2026-07-30。本次围绕「下载各种数据并处理成各种能用的格式」这个核心定位，
> 把导出格式从「绑定数据源」改成「绑定数据类型」，并新增 7 种文件格式。

---

## 一、这次解决了什么

改之前，能出什么格式取决于**数据是谁下载的**，而不是**数据本身是什么**：

| 数据源 | 改前可出格式 |
|--------|------------|
| 影像 | GeoTIFF / TMS 瓦片 / OSM 瓦片 |
| 地形（DEM） | 高程 GeoTIFF / 原始 LERC 瓦片 / Cesium 地形切片 |
| 三维建筑 | 3D Tiles / GeoJSON |

三条管线的格式清单互不相通。地形出不了瓦片，不是技术做不到，纯粹因为这层绑定。
加一种格式要改五六处代码（阶段定义、执行器、清理逻辑、产出收集、界面三个 tab）。

现在格式声明的是「我接受哪种数据类型」，与数据源无关。地形因此自动获得了
切瓦片的能力，新增格式只需在一张表里加一行。

---

## 二、新增的格式

### 栅格类

| 格式 | 适用 | 说明 |
|------|------|------|
| **COG（云优化 GeoTIFF）** | 影像 / 地形 | 仍是合法 GeoTIFF，老软件照样能读，但多了内部分块与金字塔，大图在 QGIS 里拖动、缩放明显更快。与普通 GeoTIFF 并列可选 |
| **PNG + worldfile** | 影像 / 地形 | 出图、汇报用。附带 `.wld` 记录坐标 |
| **JPEG + worldfile** | 影像 | 有损压缩，体积小。地形不开放此格式（会丢高程精度） |
| **ASCII Grid** | 地形 | 纯文本高程网格，老一些的分析软件常要这个 |
| **XYZ 高程点** | 地形 | 逐点文本，体积大，适合小范围 |

### 瓦片类

| 格式 | 适用 | 说明 |
|------|------|------|
| **MBTiles** | TMS / OSM 瓦片 | 把几千上万个碎瓦片装进**单个文件**。拷盘、发给同事都方便得多——小文件多的时候拷贝会慢到离谱 |

### 矢量类

| 格式 | 适用 | 说明 |
|------|------|------|
| **GeoPackage（GPKG）** | 建筑轮廓 / 等高线 | 单文件、无字段名长度限制、UTF-8 无编码坑。**优先选它** |
| **Shapefile** | 建筑轮廓 / 等高线 | 国内项目交付常硬性要求。注意字段名上限 10 字符（见下方提醒） |

### 新的处理能力

| 能力 | 说明 |
|------|------|
| **地形 → TMS / OSM 瓦片** | 高程先渲染成晕渲灰度图再切片，可直接当底图叠加看地形起伏 |
| **地形 → 等高线** | 输出矢量线，带「高程」属性字段。等高距可在界面设置（默认 50 米） |

## 三、界面上怎么用

### 文件格式下拉

在「2. 下载参数」里勾选导出格式后，**下方会自动出现对应的「文件格式」下拉**——
只有确实有多个选择时才出现（比如 Cesium 地形切片结构固定，就没有这一项）。

- 影像 tab：勾 GeoTIFF 后可选 GeoTIFF / COG / PNG / JPEG；勾 TMS 或 OSM 后可选瓦片目录 / MBTiles
- 地形 tab：勾高程 GeoTIFF 后可选 GeoTIFF / COG / ASCII Grid / XYZ / PNG；勾等高线后可选 GeoJSON / GPKG / Shapefile
- 三维建筑 tab：建筑轮廓可选 GeoJSON / GPKG / Shapefile

下拉旁的 ⓘ 图标会说明该格式的取舍，以及**附属文件清单**——Shapefile 这类多文件
格式，拷贝时少带一个 `.prj` 就会丢坐标系。

### 等高距

地形 tab 勾选「等高线（矢量）」后出现「等高距（米）」输入框。

可填 1–1000 米，默认 50。30 米级 DEM 上 50 米比较合适。设得过小（比如 5 米）会因
源数据精度不足产生大量锯齿状线条，不是更精确，只是更乱。

等高线取的是所选**最高级别**的高程数据；已勾选高程 GeoTIFF 时直接复用那张合并图，
不重复拼接。

## 四、两个要留意的地方

### Shapefile 会截断字段名

Shapefile 格式规定字段名最长 10 个字符，超长的会被**静默截断**：

```
base_height  →  base_heigh
```

数据本身没问题，但字段名变了。日志里会给出提示。**需要完整字段名就选
GeoPackage**——同样的数据，GPKG 里 `base_height` 是完整的。

### 容器是「换一种装法」，不是「多一份成果」

选了 COG，输出目录里就只有 COG，不会同时留一份普通 GeoTIFF。
选了 MBTiles，瓦片目录会被打包进单文件后删除。

这么设计是为了避免「到底该拷哪个」的困惑。需要两种格式请分别建两个任务。

## 五、成果文件名对照

| 阶段 | 默认（旧行为） | 选了其他格式 |
|------|--------------|------------|
| 影像合并 | `名称_z13.tif` | COG 同名；PNG 为 `名称_z13.png` + `.wld` |
| 高程 | `名称_dem_z13.tif` | ASCII Grid 为 `名称_dem_z13.asc` + `.prj` |
| 晕渲图 | `名称_hillshade_z13.tif` | 跟随高程的格式选择（两者由同一阶段产出） |
| TMS 瓦片 | `tms/` 目录 | `名称_tms.mbtiles` |
| OSM 瓦片 | `osm/` 目录 | `名称_osm.mbtiles` |
| 等高线 | `名称_contour.geojson` | `名称_contour.gpkg` / `.shp`（含 5 个附属文件） |
| 建筑轮廓 | `名称_buildings.geojson` | `名称_buildings.gpkg` / `.shp` |

## 六、兼容性

**已有任务不受影响。** 库里 73 条历史任务的阶段构成与成果路径全部保持原样，
已完成的任务可以照常重跑、单阶段重试。旧任务没有「文件格式」这项设置，
按各阶段的默认格式处理（与改前完全一致）。

**默认行为没变。** 不动新增的下拉，导出的东西和以前一模一样。

## 七、给开发者：加一种格式要改哪里

格式定义集中在 `backend/core/formats.py`，三个概念分开建模：

- **DataKind** — 数据是什么（影像栅格 / DEM 栅格 / 矢量面 / 矢量线 / 瓦片目录 / 3D Tiles / 地形切片）
- **ExportStage** — 做什么处理（geotiff / tms / osm / dem / terrain / contour ...）
- **Container** — 写成什么文件（GTiff / COG / GPKG / Shapefile / MBTiles ...）

容器必须与阶段分开：COG、GPKG、SHP 本质是「同一个阶段的不同写出方式」，
若平铺成独立格式，阶段数会按「容器 × 阶段」组合爆炸，且「同时出 tif 和 cog」
这类需求无法表达。

**加一种容器**：在 `CONTAINERS` 加一行，声明它接受哪些 DataKind；
在对应 ExportStage 的 `containers` 里登记。界面会自动出现该选项
（前端读 `/api/capabilities`，不硬编码格式列表）。

**加一种阶段**：在 `STAGES` 加一行，并在 `runner._executors_for` 给出执行器。
两者的一致性在模块导入时校验（`_assert_executors_cover`）——声明了却没实现会
**启动即报错**，而不是让用户勾选后得到一个空转的阶段、任务显示成功但目录里什么都没有。

依赖方面新增了 `pyogrio==0.13.0`（矢量写出）。它自带一套 GDAL，与 rasterio 那套
并存，打包体积因此从 153 MB 增至 255 MB。`.spec` 里必须 `collect_all("pyogrio")`
并显式声明其 cython 子模块，漏收的话影像/地形管线看着正常、只有矢量格式失效。
