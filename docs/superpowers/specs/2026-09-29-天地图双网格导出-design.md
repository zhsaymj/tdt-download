# 天地图双网格导出(tms+osm 同选时下两套原始瓦片) — 设计文档

> 日期:2026-09-29
> 关联:需求37(TMS 重投影核)、需求38(OSM 断层策略)之后的延续
> 状态:**待确认**

---

## 1. 问题与目标

### 现状

导出格式各有**原生网格**:

| 格式 | 原生网格 |
|---|---|
| `tms` | gdal2tiles **geodetic**(EPSG:4326) |
| `osm` | Web 墨卡托 XYZ(EPSG:3857) |

而数据源能提供的网格不一样:

| 源 | geodetic(4326) | mercator(3857) |
|---|---|---|
| 天地图 | ✅ `img_c`/`vec_c`/`ter_c` | ✅ **`img_w`/`vec_w`/`ter_w`** |
| Google / Esri | ❌ | ✅ |
| 本地文件 / DEM | 无下载环节 | |

于是**跨网格的那一种格式必然要重投影**:

| 情形 | tms | osm |
|---|---|---|
| 天地图 | ✅ 无损直映射 | ❌ 需 4326→3857 重投影 |
| Google / Esri | ❌ 需 3857→4326 重投影 | ✅ 3857→3857 不重投影 |

需求37 已把「默认勾选的格式」调成各源无损的那一种(天地图默认 `tms`、
Google/Esri 默认 `osm`),所以**默认路径上已经不重投影**。剩下的缺口是:
用户手动跨网格选格式时(尤其天地图选 `osm`,以及两个格式都要时)。

### 目标

**天地图任务同时勾了 `tms` 与 `osm` 时,按各自的原生网格下载两套瓦片,使两个
格式都无损**(不再由我们客户端重投影其中一种)。

### 非目标(本次不做)

- **不给 Google/Esri 补 geodetic 网格** —— 它们根本没有 `_c` 那套。这类源出
  `tms` 仍然必须重投影,由需求37 的 cubic 核兜着质量。
- **不引入"用哪套网格渲染更好"的自动判断** —— `_c` 与 `_w` 是同一份影像的两套
  渲染,不是"更高清"。收益只在**不引入重投影损失**。
- 不改 TMS 的 geodetic 语义、不改 OSM 的 3857 语义。

### 已确认的取舍

1. **下载量约 2×**(两套瓦片不同网格、不能互相替代),且**天地图 tk 配额也约 2×**。
   这是用户明确选择的方向("按照导出格式下载两套原始数据效果最好")。
2. **只在两个格式都选时才下两套**。只选一个时不下多余的 —— 需求37 已保证那种
   情况下默认格式就是无损的。
3. 预估(瓦片数/体积)**必须跟着显示 2×**,否则用户看到实际下载量是预估的两倍
   会以为出 bug。

## 2. 核心设计决策

### D1:网格需求由「导出格式」推导,不新增用户选项

| 格式 | 需要的网格 |
|---|---|
| `osm` | mercator |
| `tms` | geodetic |
| 其余(`geotiff`/`dem`/`terrain`/`contour`/`tiles`) | 不限,用源的默认网格 |

新增一个**纯函数**(单一判定处):

```
def download_grids_of(provider, export_formats) -> set[str]
    """该任务实际要下载哪些网格。
    源的默认网格来自 PROVIDER_GRID;若请求的格式需要另一种网格且该源提供它
    (目前只有天地图两套都有),就一并下载。
    """
```

推导得出:

| 任务 | 结果 |
|---|---|
| 天地图 + `tms` | `{geodetic}` |
| 天地图 + `osm` | `{mercator}` |
| 天地图 + `tms,osm` | **`{geodetic, mercator}`** ← 本次的核心情形 |
| Google + `osm` | `{mercator}` |
| Google + `tms,osm` | `{mercator}`(tms 仍重投影,无法避免) |

**不落库、不加 DB 字段**:推导是纯函数,预估接口与 worker 调同一个即可保持一致
(与 `z_cap_of` 集中判定的做法一致 —— 见 `core/formats.py` 里那条"级别的唯一判定处")。

### D2:缓存键必须带上网格(本设计的**硬约束**)

现路径:`{cache}/{provider.key}/{z}/{col}_{row}.{ext}`,而 `provider.key` 恒是
`tianditu_img` —— **不含网格**。

`_c` 用 geodetic 行号、`_w` 用 XYZ 行号,第 z 级行数分别是 `2^(z-1)` 与 `2^z`,
**同一个 `(col, row)` 指的不是同一地点**。两套混进同一目录会:

- 互相覆盖(后写的赢)
- 断点续传时把另一套网格的瓦片当成命中,拼接出**静默错乱**的成果

故缓存路径改为 `{cache}/{key}_{grid}/{z}/{col}_{row}.{ext}`,例如:

```
data/tiles/tianditu_img_c/12/3348_1674.jpg     ← 现状(geodetic)
data/tiles/tianditu_img_w/12/3348_3348.jpg     ← 新增(mercator)
```

**旧缓存怎么办**:目录名从 `tianditu_img` 变成 `tianditu_img_c`,老缓存会"失联"。
两种处理:

- (a) 不做迁移,老缓存留在原地不再命中(下次跑会重新下载)——**简单、无风险**
- (b) 启动时一次性把 `{key}/` 改名为 `{key}_c/`(仅天地图三兄弟 + 注记)

> **建议 (b)**,理由:老缓存里有用户已经下好的大量天地图瓦片 —— **实测
> `tianditu_img` 18 个级别共 181,777 张**(单 z18 就 85,075 张),不迁移等于白下。
> 改名是一次性的目录 rename,不涉及内容解析,失败可回退(改名失败就当 (a))。
>
> ⚠️ 注记那几个 key(`tianditu_cia/cva/cta`)现有缓存**全是 `_w`**(实测
> `tianditu_cia` 有 159,346 张),要按 `_{grid}` 的规则迁成 `_w`,**不能默认按 `_c`**。

### D3:天地图的两套网格用两个 provider 实例,`grid` 显式传参

`TiandituProvider` 已支持 `matrix_set='c'|'w'`(注记就是这么用 `cia_w` 的),
但:

- 它的 `key` 不带网格 → 缓存键修正见 D2
- `_range_fn_for(provider)` 目前**只看 provider 名**就决定用哪套行列号函数 →
  对天地图会恒用 geodetic。改为**显式传网格**:`_range_fn_for(grid)`

这样"同一个 provider 名、两套网格"才成立。

### D4:OSM 的源改为「按需拼 mercator 源」

现状:OSM 的源 = 源的默认网格拼接图(天地图 → 4326),再由 `export_osm` 里的
`WarpedVRT` 逐瓦片重投影成 3857。

改为:`_osm_source_for_level` 在**该源有 mercator 缓存**时,拼一张 **3857** 的源
(从 `_w` 缓存读),`export_osm` 的 WarpedVRT 就成了 **3857→3857 的空操作** →
**零重投影**。

这正是 Google/Esri OSM 现在的情形(它们只有 3857,所以一直是无损的)—— 本次是把
天地图也拉到同一状态。

> 实现上**不需要**新写"按网格无损搬运"的切片器:`export_osm` 已经是"读窗口→缩到
> 256→写 PNG",源与目标同网格时窗口换算退化为整数、无重采样。对照物是 TMS 路的
> `export_tms`(geodetic 源无损直映射),那条路本次**不动**。

### D5:预估与元数据

- **预估**(`/api/tasks/estimate`):按 `download_grids_of` 把要下的网格各计一遍,
  返回里加一个说明字段(如 `grids: ['geodetic','mercator']`),前端据此显示
  "含双网格,瓦片数已按两套计"。
- **metadata.json**:`tile_matrix_set` 现在只记一个值。改为按实际下载的网格记录
  (如 `"c (EPSG:4326) + w (EPSG:3857)"`),并在 `outputs` 里标注哪个格式来自哪套网格。

## 3. 实现设计

### 3.1 `backend/core/formats.py`:新增网格推导(单一判定处)

```python
#: 各导出格式需要的网格。未列出者不限(用源的默认网格)。
_FORMAT_GRID = {"osm": GEO_MERCATOR, "tms": GEO_GEODETIC}

def download_grids_of(provider: str, export_formats) -> list[str]:
    """该任务实际要下载哪些网格(升序稳定顺序)。"""
```

规则:从源默认网格出发,遍历请求格式需要的网格;**只有源确实提供该网格**时才加入。
"源提供哪些网格"集中在一处登记:

```python
#: 数据源原生提供哪些网格。未登记者只有自己的默认网格。
PROVIDER_GRIDS: dict[str, tuple[str, ...]] = {
    "tianditu_img": (GEO_GEODETIC, GEO_MERCATOR),
    "tianditu_vec": (GEO_GEODETIC, GEO_MERCATOR),
    "tianditu_ter": (GEO_GEODETIC, GEO_MERCATOR),
}
```

### 3.2 `backend/providers/tianditu.py`:key 带网格

`TiandituProvider.key` 由 `key` 改为 `f"{key}_{matrix_set}"`(如 `tianditu_img_w`)。
⚠️ 这会让**所有**引用 `provider.key` 的地方(缓存路径、`build_annotation_provider`、
服务扫描)跟着变 —— 需要一次全面核对,不能只改一处。

### 3.3 `backend/core/runner.py`:按网格下载

- `_range_fn_for` 改为接受网格
- `_stage` 的下载阶段:对 `download_grids_of` 的每个网格各构造一个 provider、
  各下一个 `range_for_bbox`(或 mercator 版)
- `_ctx_grid` 仍表示**主网格**(源的默认网格),驱动 COG/TMS/metadata;OSM 的主网格
  恒为 mercator(D4)

### 3.4 `_osm_source_for_level`:拼 mercator 源

按 D4,在该源提供 mercator 时,从 `_{w}` 缓存拼 3857 源(而非复用 4326 的
`{name}_z{z}.tif`)。裁剪任务仍用"裁剪前留存"的机制,留存的那份也要是 3857 版
→ `_stage_geotiff` 里 `_osm_keep` 那段要按网格分别留存。

### 3.5 前端

- **预估区**:双网格时显示提示("该任务按 tms/osm 各自的原生网格下载两套数据,
  瓦片数与体积已按两套计")
- **格式勾选区**:天地图勾了 `tms` + `osm` 时提示"两个格式各用原生网格,都不会有
  重投影损失;代价是下载量约 2×"

## 4. 边界与错误处理

| 情形 | 处理 |
|---|---|
| 天地图只勾 `osm` | 下 `_w` 一套;`_c` 不下 |
| 天地图只勾 `tms` | 下 `_c` 一套(现状不变) |
| 天地图 `tms+osm` | 下两套(D1) |
| Google/Esri `tms+osm` | 只下 3857;tms 仍重投影(非目标) |
| 某套网格下载失败 | 按现有失败语义(该级别瓦片计入 failed);**不得**用另一套网格的瓦片顶替 —— 那会静默错乱 |
| 旧缓存未迁移 | 当作未命中,重新下载(不影响正确性) |

**必须守住的**:任一处都不得出现"按网格 A 的行列号去读网格 B 的缓存"。需求38-2
已经因为这个问题踩过一次(自拼源写死 4326 范围读 3857 缓存 → 整幅拼空),D2 是
同一条约束的系统性修法。

## 5. 测试策略

### 5.1 网格推导(纯函数,重点)

`tests/test_download_grids.py`:

- 天地图 + `tms` → `['geodetic']`;+ `osm` → `['mercator']`;**+ 两者 → 两套**
- Google + `tms,osm` → 只有 `['mercator']`(不凭空造网格)
- 未登记的 provider → 只有默认网格
- `geotiff` 等不限网格的格式不改变结果

### 5.2 缓存键隔离(行为级,**防静默错乱**)

- 同一 `(col,row,z)` 在 `_c` 与 `_w` 下落盘到**不同路径**
- 反向验证:把两套写进同一路径时,拼接结果会错 —— 用一个受控的小缓存证明
  "读到的确实是各自网格的瓦片"

### 5.3 OSM 源不再重投影(行为级)

- 天地图任务(合成缓存:同时有 `_c` 与 `_w` 两套瓦片值不同)→ 断言 OSM 瓦片的
  像素值来自 **`_w`** 那套(即"没经过重投影")
- 反向:只给 `_c` 缓存时,退化为重投影(仍能出图,不报错)

### 5.4 预估翻倍

- 天地图 `tms,osm` 的 est 瓦片数 ≈ 天地图 `tms` 的 + `_w` 那套的计数

### 5.5 旧缓存迁移

- 临时目录造 `{key}/` → 迁移后变 `{key}_c/`;注记类 key 迁成 `_w`
- 迁移失败(目标已存在/权限)→ 不抛错、退回不迁移
