# 本地数据服务与预览 — 设计文档

> 需求来源:`docs/input/新增需求/需求描述2.md` 的「新增需求和优化31」
> 日期:2026-09-21
> 范围:**只做需求31**。29(导入范围解析失败)、30(层级纹理黑色碎片)不在本次范围。

## 1. 问题与目标

### 现状

本工具当前的成果只能通过**任务**访问:

- 预览页 `/preview.html?id=<任务id>` 依赖任务记录(`PreviewApp.vue::init` 开头即校验 `id`,缺失直接报错)。
- 二维叠加走 `/output/<目录>` 静态挂载,而 `/output` 只服务 `settings.output_dir` 这一个根。
- 三维查看只认任务产出目录的 `3dtiles/`、`terrain/`。

三个后果:任务记录删了成果就打不开;工具目录外的成果(别人给的瓦片包、QGIS 导出的 3d tiles)完全看不了;别的服务想拿这些成果当数据源,没有稳定可达的地址。

### 目标

1. 在**系统界面顶栏**新增「服务」菜单,把本地目录发布成长期可访问的数据服务,提供可复制的访问地址与开关。
2. 在**预览界面**新增「添加服务图层」,把已开启的服务叠加到三维场景。
3. 在**主界面图层列表**同样能从服务添加预览,透明度 / 层级 / 定位与任务图层一致。
4. 服务按 **模型 / 影像 / 矢量 / 地形** 四类归档。

## 2. 核心设计决策

这些决策贯穿全文,先集中列出。

| # | 决策 | 理由 |
|---|---|---|
| D1 | **一个可访问端点 = 一个服务** | 让"复制访问地址"有确定语义。`output/怀化不动产_全量/` 里的 `3dtiles/` 是一个服务,`tms/` 是另一个。代价是服务数量多,用分类+筛选化解。 |
| D2 | **默认候选扫文件系统,不读数据库** | 实测:库中 106 条 `output_path` 记录,**100 条目录已不存在**(成果被清理但记录留存)。读库会生成 100 个死服务;扫 `settings.output_dir` 实际得到 6 个目录、约 8~10 个服务。 |
| D3 | **落盘持久化到 sqlite,新增服务默认关闭** | 服务是长期配置,重启后地址不能变(其他服务配一次要长期有效)。默认关闭保证"不主动暴露"。 |
| D4 | **端点不带 token,不做访问限制** | 用户明确选择。默认 `server.host = 127.0.0.1` 时实际暴露面仅本机,其他本机服务可访问;仅当改为 `0.0.0.0` 时才对局域网开放。 |
| D5 | **两条来源,一个渲染出口** | 服务图层进入 `overlays.js` 时,`desc` 结构必须与 `core/overlay.py::list_layers()` 输出**逐字段对齐**,从而零改动复用透明度/层级/定位。 |
| D6 | **服务是指向,不是拥有** | 移除服务只删注册记录,绝不动磁盘文件。任务被 purge 时服务不自动删除,只标记失效。 |

## 3. 后端设计

### 3.1 数据模型

新增 `services` 表。沿用 `db.py` 既有的 `_SCHEMA` + `_MIGRATIONS` 手动加列模式(SQLite 不支持 `ADD COLUMN IF NOT EXISTS`),新增字段需同时改 `_SCHEMA`、`_MIGRATIONS`、`models` 读写与 `_row_to_dict`。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | 短随机 id(8 位十六进制),用作 URL 段 |
| `name` | TEXT | 显示名,默认由目录推导,可改 |
| `kind` | TEXT | `model` / `imagery` / `vector` / `terrain` |
| `root` | TEXT | 服务根目录**绝对路径**,已 `resolve()`,路径穿越检查的基准 |
| `entry` | TEXT | 相对 root 的入口。TMS 为 `""`;模型为 `tileset.json`;矢量为文件名 |
| `grid` | TEXT | 瓦片网格:`geodetic` / `mercator` / `""`(非瓦片) |
| `flip_y` | INTEGER | 行号是否自南向北(TMS 为 1,OSM 为 0) |
| `minzoom` / `maxzoom` | INTEGER | 瓦片级别范围 |
| `bounds_wgs84` | TEXT | JSON 数组 `[w,s,e,n]`,供定位。来源见 3.1.1;取不到为 NULL,前端需有兜底 |
| `bounds_approx` | INTEGER | 范围是否为估算值。两个来源会置 1:`tilemapresource.xml` 的瓦片对齐四至(§3.1.1 优先级 2)、索引扫描超限降级(§3.1.2)。前端据此提示"范围约为估算值" |
| `enabled` | INTEGER | 开关,**默认 0** |
| `source` | TEXT | `output_scan` / `manual` |
| `created_at` | TEXT | ISO 时间 |

#### 3.1.1 范围来源(`bounds_wgs84`)

按优先级取第一个命中的。前两类是**元数据直读**,后三类是**反算**——其中瓦片索引反算是关键,它让**没有任何元数据的 OSM/XYZ 瓦片包也能定位**。

| 优先级 | 类别 | 来源 | 说明 |
|---|---|---|---|
| 1 | 全部 | 同级 `metadata.json` 的 `bbox_wgs84` | 本工具产出的成果都有,最准 |
| 2 | 影像 | `tilemapresource.xml` 的 `BoundingBox` | 属性名是 **`minx` / `miny` / `maxx` / `maxy`**(不是 `west` 等)。**实测该值是"瓦片对齐后的四至"(`tms.py::write_tilemapresource` 用 `mosaic_bounds()` 生成),比真实选区每边最多大出一张瓦片**,故定位够用但不是精确范围。读到它时置 `bounds_approx = 1` |
| 3 | 模型 | `tileset.json` 的 `root.boundingVolume` | **两种形态都要支持**:`region` 为 `[west,south,east,north]` **弧度**,直接转度;`box` 是 `[cx,cy,cz, xAxis..., yAxis..., zAxis...]`(中心 + 三个半轴向量,地心 ECEF 米制),**实测本工具产出的用 `box`**。`box` 取八个角点后取 min/max,再用 `rasterio.warp.transform` 从 EPSG:4978 转 4326。两者都没有时 → 降级为 NULL |
| 4 | 地形 | `layer.json` 的 **`available`** | **不要用 `bounds`**:实测本工具切出的地形 `bounds` 恒为 `[-180,-90,180,90]`(写的是世界范围,不是数据范围)。`available` 是逐级的 `{startX,startY,endX,endY}` 区间(y 自南向北),取最高级用 **`terrain_tiles.py::geodetic_tile_bounds`** 反算——**注意用第三套网格,不是影像 TMS 的**,见 §3.1.2。实测可用,置 `bounds_approx = 1` |
| 5 | 影像 | **扫描瓦片索引区间反算** | 见下,OSM/裸 XYZ 包的兜底 |
| 6 | 矢量 | **解析几何范围** | 复用 `local_vector_file.inspect_vector()`(内部用 `pyogrio.read_bounds` + `rasterio.warp.transform_bounds`)。**实测 `.kml` 与 `.geojson` 都能读**,同源数据得到完全一致的范围。GeoJSON 需**先转出**才能算:**KML 统一转 GeoJSON(§4.3)**,所以注册时解析的是转出的那份 |

> **优先级 6 是必须实现的,不是可选优化。** 现有 `core/overlay.py::list_layers()` 的矢量项**不带 `bounds_wgs84`**——它靠 `overlayStore._fallbackBbox(taskId)` 拿任务 bbox 兜底。**服务图层没有任务,这个兜底必然返回 null,矢量服务的定位会直接失效。** 实现时若照抄现有 desc 结构就会漏掉这一步,必须显式补上。

#### 3.1.2 瓦片索引反算(优先级 5)

**原理**:扫描瓦片目录得到每个级别的行列区间,用该级别的外接矩形反算经纬度。取**最高级别**的区间——低级别瓦片覆盖范围更粗,高级别最贴合实际数据。

复用项目既有换算函数,不新写坐标逻辑。**项目里有三套互不相同的瓦片网格,必须按数据类型选对**——三者的 `tile_bounds` 函数签名相似、返回值都是四至元组,**用错了不会报错,只会静默得到一个看似合理却完全错误的范围**:

| 网格 | 用于 | 复用函数 | 行/列定义 |
|---|---|---|---|
| 影像 TMS(geodetic) | 天地图影像瓦片、`tms/` 目录 | `core/tiling.py::tile_bounds(col, row, z)` | 列 `2^z`、行 `2^(z-1)`,span `360/2^z`。**行号先翻转**走 `core/tms.py::tms_row()`(`xyz_row = 2^(z-1) - 1 - tms_row`) |
| Web 墨卡托(mercator) | OSM XYZ、`osm/` 目录 | `core/osm.py::tile_bounds_3857(x, y, z)` | 列 `2^z`、行 `2^z`。得 3857 米制四至,再 `rasterio.warp.transform_bounds(crs=3857, "EPSG:4326", densify_pts=21)` 转度 |
| **Cesium 地形 geodetic** | `terrain/` 目录、`layer.json` 的 `available` | **`core/terrain_tiles.py::geodetic_tile_bounds(x, y, L)`** | **列 `2^(L+1)`、行 `2^L`,span `180/2^L`**,y 自南向北(0 在 -90°),**无需翻转** |

第三套最容易错:`terrain_tiles.py` 的网格与 `tiling.py` 的完全不同(它的 L=0 是 2×1 张瓦片覆盖全球,而 `tiling.py` 的 z=0 是 1×1)。**地形范围必须走 `geodetic_tile_bounds`,不能图省事复用 `tiling.py`。**

**实测验证**(`output/新疆矿_高程/`,L=12 区间 x:[6120,6129] y:[3063,3070]):反算得 `[88.945312, 44.604492, 89.384766, 44.956055]`,与 `metadata.json` 的原始选区 `[88.975611, 44.640284, 89.346399, 44.917688]` 相比每边外扩 0.03~0.04 度(单瓦片跨度 0.044 度),**完整包含真值**。定位够用,但需置 `bounds_approx = 1`。

**目录命名要支持两种**(扫到哪种用哪种):

- `{z}/{x}/{y}.png` —— gdal2tiles / OSM XYZ 标准结构(本工具导出成果)
- `{z}/{col}_{row}.ext` —— 本工具瓦片缓存格式(用户把缓存目录当服务发布时)

**性能保护**:扫描量为文件数。设 **20 万文件上限**;超限则用已扫到的部分并置 `bounds_approx = 1`,前端提示"范围约为估算值"。实测本工具单任务成果在万级,上限内必命中。扫描在**注册时执行一次**,不进入请求路径。

#### 3.1.3 网格类型的判定

反算前要先知道是 geodetic 还是 mercator:

1. 有 `tilemapresource.xml` → 读 **`<TileSets profile="...">` 的 `profile` 属性**(实测本工具写的是 `geodetic`)。它比 `<SRS>` 更直接——`SRS` 只说明坐标系,`profile` 直接是网格名。
2. 无 XML → 看**第 1 级瓦片的行数**:geodetic 的 z=1 只有 1 行(行数 `2^(z-1)`),mercator 有 2 行(行数 `2^z`)。这是两者的结构性差异,不依赖命名约定。
3. 仍判不出 → 默认 **mercator**(XYZ 是更通用的约定),并由用户在注册时手工覆盖。

`flip_y` 与网格绑定:geodetic TMS 目录形态为 1(行号自南向北),mercator 为 0。与 `core/overlay.py::list_layers()` 的判定保持一致。

#### 3.1.4 范围仍为 NULL 时

前端不猜测:定位按钮置灰并提示"该服务没有范围信息,无法定位"。三维类不受此影响——预览页改用 `viewer.zoomTo(tileset)`,不依赖 `bounds_wgs84`;主界面只画范围框,范围框缺失时该服务的定位按钮同样置灰。

**注意**:§3.1.1 的优先级 3/4 都是**尽力而为**的解析。三维数据即使全部解析失败也能用(靠 `zoomTo`),而瓦片类失去范围就只剩手工目视找位置——所以优先级 5 的索引反算是瓦片类的主路径,不是可有可无的兜底。

### 3.1.5 定位的执行方式(按类型)

范围只是参数,**定位动作本身因端而异**。下表是实现的直接依据:

| 类型 | 主界面(OpenLayers) | 预览页(Cesium) | 无范围时的行为 |
|---|---|---|---|
| **影像·TMS** | 瓦片图层,`view.fit(transformExtent(bounds))` | 影像图层,`camera.flyTo({destination: Rectangle.fromDegrees(...)})` | 按钮置灰 + 提示 |
| **影像·OSM** | 同上(mercator 网格,同样走 `transformExtent`) | 同上 | 按钮置灰 + 提示 |
| **影像·tif** | `WebGLTileLayer`,同 `fit` | 预览页不加载 tif(与现有任务流程一致) | 按钮置灰 + 提示 |
| **矢量** | `VectorLayer`,`view.fit(extent)` | Ground Primitive | 按钮置灰 + 提示 |
| **地形** | ⚠️ 不支持渲染,**只画范围框**(与现有 `preview3d` 处理一致) | `viewer.terrainProvider` + `camera.flyTo` | 按钮置灰 + 提示;范围框也不画 |
| **模型** | ⚠️ 同上,只画范围框 | `viewer.zoomTo(tileset3d)`——**不依赖 `bounds_wgs84`** | **预览页仍可定位**(`zoomTo` 用瓦片集自身包围盒);主界面按钮置灰 |

**三个要点**:

1. **模型是唯一在预览页脱离范围也能定位的类型**。主界面因为它只能画范围框,反而依赖范围——所以模型服务的范围解析(优先级 3)仍要做,只为二维的范围框。
2. **地形/模型在主界面不支持渲染**,这是 `overlays.js::build()` 的既有能力边界(它只认 `tiles`/`cog`/`vector`/`vector_convert`/`raster_only_bbox`),不是本次引入的缺陷。
3. **定位失败必须给反馈**。`LayerPanel.vue::locate()` 已有 `MessagePlugin.warning('该图层没有可用的范围信息,无法定位')`,`overlayStore.zoomTo()` 返回 false 即触发——服务图层复用这条既有路径即可,不新写提示。

### 3.2 成果识别规则

新增 `backend/core/service_scan.py`。判据取自**格式规范定义的标志文件**,不是目录命名约定——因此对任意第三方瓦片包同样成立。

| 类别 | 判据 | 实测命中示例 |
|---|---|---|
| 模型 | 递归找到 `tileset.json` | `output/Data/3dtiles/` |
| 地形 | 目录含 `layer.json` | `output/新疆矿_高程/terrain/` |
| 影像 | 含 `tilemapresource.xml`(TMS);或含数字分层子目录且层内有瓦片(OSM/XYZ);或单个 `.tif` | `*/tms/`、`*/osm/` |
| 矢量 | 单个 `.geojson` / `.kml` | `*_contour.geojson` |

**扫描深度限制为 3 层**;只认上述判据文件。识别不出时**回退到手工指定类型**注册(接口接受显式 `kind`),不静默忽略。

扫描不出的常见原因要提示到位:只有裸目录结构、连 `tilemapresource.xml` 都没有的 TMS。

### 3.3 端点

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/services` | 列出已注册服务(含 `enabled`、`overlay_desc`、`access_path`) |
| GET | `/api/services/candidates` | 扫 `settings.output_dir` 得到的候选(未注册的) |
| POST | `/api/services/scan` | 扫任意本地目录 → 候选 |
| POST | `/api/services` | 注册 |
| PATCH | `/api/services/{id}` | 改名 / 开关 |
| DELETE | `/api/services/{id}` | 移除注册记录(**不删文件**) |
| GET | `/api/services/health` | 批量探活,面板打开时调用 |
| GET | `/api/svc/{id}/{path:path}` | **文件服务** |

**`access_path` 返回路径而非完整 URL**:后端只知道 `server.host`(可能是 `127.0.0.1`),而实际访问者可能是 `192.168.x.x` 或域名。前端拼 `location.origin`。

### 3.4 文件服务的安全与错误语义

- `root` 在注册时 `resolve()`。每个请求把 `root/entry/path` 拼接后 `resolve()`,必须 `is_relative_to(root)` → 否则 **403**。`..` 穿越、绝对路径注入、短路径、大小写变体、符号链接逃逸全部过这同一道检查。
- `enabled = 0` → **403 + JSON 说明**("服务未开启")。开关状态与路径写错是两回事,报错必须能区分。
- root 或 entry 不存在 → **410 Gone** + 明确文案("源目录已不存在"),前端据此把卡片标灰。
- **必须处理 Range 请求**(返回 206):`ol/source/GeoTIFF` 直读 tif 依赖它,这是现有 `overlays.js` 里 `cog` 类型的既有前提。
- 3D Tiles 的 `.pnts` / `.b3dm` / `.json` 需正确的 `Content-Type`。
- **不做来源限制**(D4)。代码注释与文档写明:仅当 `server.host` 为 `0.0.0.0` 时才对局域网开放。

### 3.5 服务生命周期与失效处理

服务是持久化的,但磁盘上的目录不是。目录被删/移走后卡片仍在列表,因此必须有移除入口。

| 状态 | 判据 | 卡片表现 | 可用操作 |
|---|---|---|---|
| 已开启 | `enabled=1` 且源存在 | 绿色标记 | 关闭 / 复制地址 / 移除 |
| 已关闭 | `enabled=0` 且源存在 | 灰色标记 | 开启 / 移除 |
| **源失效** | root 或 entry 不存在 | 红字「源目录已不存在」+ 整卡降透明度 | **仅移除**(开启/复制禁用) |

**移除入口三层**:

1. **卡片上的「移除」按钮** — 每个卡片自带,`Popconfirm` 二次确认。**失效状态下依然可点**——目录没了正是最需要移除的时候。
2. **「清理全部失效服务」** — 面板顶部,仅当存在失效服务时出现。文案需提醒:外接盘未挂载时服务会集体假性失效,避免误清。
3. **`DELETE /api/services/{id}`** — 只删注册记录(D6)。

**检测时机**:面板打开时调 `GET /api/services/health` 批量探测一次(纯本地 `Path.exists()`,毫秒级)。不做常驻轮询——目录被删是低频事件。

**与任务删除的关系**:任务被 `purge=True` 删除时 output 目录消失,对应服务随即失效,但**不自动删除服务记录**。自动删会让"目录临时不可用(外接盘没挂上)"变成永久丢失配置。

### 3.6 复用既有能力

- **系统文件对话框**:`POST /api/local/pick`(`kind='dir'` / `'file'`)已实现且有 `DIALOG_TIMEOUT` 与线程池处理,直接复用,不新写。
- **成果扫描**:`core/overlay.py::list_layers()` 的判定逻辑(瓦片扩展名探测、级别范围、`_tiles3d_entry` 多文件点云子目录约定)可提取复用。
- **矢量转换**:`core/local_vector_file` 已有 pyogrio 能力,用于 KML → GeoJSON(见 4.3)。

## 4. 前端设计

### 4.1 服务面板

**入口**:`AppTopBar.vue` 在「任务」之后加「服务」按钮,角标显示**已开启服务数**(对齐现有 `activeCount` 的角标做法)。点击打开 `ServicePanel.vue`(右侧抽屉)。

**布局**:

```
┌─ 服务 ──────────────────────────────── [×] ┐
│ 本地目录: [路径输入________] [浏览…] [扫描]  │  ← 顶部:添加
├────────────────────────────────────────────┤
│ ⚠ 发现 2 个失效服务      [清理全部失效]      │  ← 仅失效时出现
```

#### 4.2.1 改造时必须处理的四个既有陷阱

这四处是核实现有代码时发现的,不处理会导致新功能**静默失效或直接崩**:

**(1) `viewer` 创建时机必须提到 `id` 判断之前**

现有顺序:`:203` 校验 `id` → `:207` fetch 任务 → `:264` 创建 viewer → `:271` `createCesiumMeasure(viewer)`。

`measure3d.js` 内部强依赖非空 viewer(`:306` 注册 `camera.moveEnd`、`:504` `new ScreenSpaceEventHandler(viewer.scene.canvas)`)。**若只去掉 `:203` 的早退而不重排顺序,空白预览要么没有 viewer,要么 measure 拿到 null 直接崩。** 需把 viewer 创建与底图/天地图密钥加载(`:258-300`)整体前移。

**(2) `fetch` 对 404 不抛错,需显式判 `res.ok`**

`backend/api/tasks.py` 对不存在的任务返回 `HTTPException(404, "任务不存在")`,body 是合法 JSON,**`fetch` 照常 resolve**。现状带一个不存在的 id 打开,会静默渲染空预览、顶栏显示 `/output/undefined`(`outputBase(undefined)` → `String(undefined)`),不报任何错。改造需显式判 `res.ok`,与"缺少 id"走不同的分支。

**(3) `applyTerrain()` 的三元兜底会吞掉服务地形**

现有 `:160-162` 是硬编码 `if (activeKey === 'terrain') ... else if (activeKey === 'terrain-national') ... else flatTerrain`。**只把服务地形的 key 加进 `TERRAIN_KEYS` 是不够的**——互斥重置会正确执行(界面看起来正常),但 activeKey 落入 `else` → `terrainProvider` 被设为平面椭球,**地形永远不出现且不报错**。

须重构为 **key → provider 的映射表 + 按需异步 ensure**(现有 `ensureNationalTerrain` 的 `:137-151` 与 `:170-181` 是模板)。且 `applyTerrain` 当前是同步函数,服务地形需要 `await CesiumTerrainProvider.fromUrl(...)`,签名要改成 async。

顺带:`:498` 的提示文案"两个地形数据互斥"在加入第三个地形源后不准确,需改成不依赖数量。

**(4) `tileset3d` 单变量在多个 3D Tiles 下互相干扰**

全文件**只有 `primitives.add`(`:388`),没有任何 `primitives.remove`**。加载第二个瓦片集后:

- 场景里两个都在(`PrimitiveCollection` 不覆盖),但 `tileset3d.show`(`:193`)只控制**最后一个**——先加载的**永远可见且无法关闭**;
- `:106` 的 `if (!tileset3d)` 判定失真,只要有任意一个就走 45° 斜视分支;
- `:401` 的 `zoomTo(tileset3d)` 只定位最后一个;
- **无卸载路径**:`onBeforeUnmount`(`:432`)只做 `viewer.destroy()`,移除服务时不释放 GPU 资源,会内存泄漏。

须改为 `Map<serviceKey, tileset>`,toggle 按 key 取实例,移除时 `viewer.scene.primitives.remove(tileset)`。

**另**:`flyToBbox()`(`:103-121`)无参,依赖模块级 `taskBbox` 与 `tileset3d`。服务图层定位必须**参数化**(`flyToBbox(bbox, has3d)`),否则会飞到任务范围或直接 return。

**测试联动**:`TaskQueue.model3d.test.js:95-115` 用**源码文本断言** `PreviewApp.vue`(断言含 `'viewer.zoomTo(tileset3d)'`、`'taskBbox.every((v) => v === 0)'`)。改动这些行会打断该测试,需同步更新断言。

### 4.3 矢量贴地渲染

需求要求"用 primitive、贴地"。Cesium 的实际能力分布:

| 几何 | 贴地方案 | 是否 Primitive |
|---|---|---|
| 面 | `GroundPrimitive` + `GeometryInstance` + `ColorGeometryInstanceAttribute` | 是 |
| 线 | `GroundPolylinePrimitive` + `GroundPolylineGeometry` | 是 |
| 点 | **无贴地 Primitive** | 否,需破例 |

**点要素的处理(用户已确认)**:默认用 **Entity + `heightReference: CLAMP_TO_GROUND`**;当单图层点数**超过 5000** 时自动回退为不贴地的 `PointPrimitive` 并提示用户。代码注释必须写明为什么点要破例,避免后人误以为是随手写法。

**KML 的处理**:`KmlDataSource` 走 Entity 体系,与"用 primitive"冲突。因此 **KML 统一在后端转成 GeoJSON**(复用 `core/local_vector_file` 的 pyogrio 能力),前端只处理 GeoJSON 一种输入。

#### 4.3.1 实现前必须知道的三个 API 事实

**(1) 静态工厂方法在本项目所用版本中已移除**

`GroundPrimitive.fromPolygonHierarchy` / `fromRectangles`、`GroundPolylinePrimitive.fromPositions` **在 cesium 1.143(engine 26.1.0)中均不存在**(全仓 `grep fromPolygonHierarchy` 零命中;`GroundPrimitive` 的 static 成员只有 `isSupported` / `initializeTerrainHeights` / `supportsMaterials`)。

**必须手搓构造**:

```
面 → new GroundPrimitive({
       geometryInstances: new GeometryInstance({
         geometry: new PolygonGeometry({ polygonHierarchy: new PolygonHierarchy(positions) }),
         attributes: { color: ColorGeometryInstanceAttribute.fromColor(color) },
       }),
       appearance: new PerInstanceColorAppearance(),
     })
线 → new GroundPolylinePrimitive({
       geometryInstances: new GeometryInstance({
         geometry: new GroundPolylineGeometry({ positions }),
       }),
       appearance: new PolylineColorAppearance(),
     })
```

**(2) 构造前必须先 `await GroundPrimitive.initializeTerrainHeights()`**

这是异步前置,不做的话贴地高度未初始化。应放在预览页初始化流程里**只调用一次**,封装进 4.3.2 的模块内并缓存 Promise。

**(3) `GeoJsonPrimitive` 存在,但**不能**用来贴地**

cesium 1.143 新增了 `GeoJsonPrimitive`(`fromUrl` 直读 GeoJSON、内部拆成 `BufferPointCollection`/`BufferPolylineCollection`/`BufferPolygonCollection`,不创建 Entity,性能优于 `GeoJsonDataSource`)。看起来很合身,但**它的构造选项只有 `ellipsoid` / `allowPicking` / `show` / `pickObjectFactory`,三个 Buffer 集合均不支持贴地**。故本次不采用——若将来需要高性能不贴地矢量,它是首选。

#### 4.3.2 封装

新建 `frontendvue/src/preview/vectorGround.js`,对外只暴露 `addVectorGround(viewer, geojson, opts)` 与 `removeVectorGround(viewer, handle)`,内部按几何类型分发到上述三条路径,并统一处理:

- `initializeTerrainHeights()` 的一次性 await 与 Promise 缓存;
- 点数阈值判定与回退提示;
- 资源释放(`primitives.remove`),与 §4.2.1(4) 的 `Map<key, tileset>` 改造同一套移除约定。

**已知限制**:`GroundPrimitive` 依赖地形做裁剪,**没有地形时退化为贴在椭球面**。这是 Cesium 固有设计,界面提示需写明。

### 4.4 主界面图层列表接入

现有 `overlayStore` 有三个与任务强绑定的假设,必须解除:

| 约束 | 现状 | 改法 |
|---|---|---|
| `overlayKey(taskId, layerId)` | key 恒为 `${taskId}:${layerId}` | **拆成两个函数**:`taskOverlayKey(taskId, layerId)` 返回 `task:${taskId}:${layerId}`,`serviceOverlayKey(serviceId)` 返回 `svc:${serviceId}`。**不要复用同一个函数换语义**——`_fallbackBbox` 里 `it.taskId` 字段的含义会被污染 |
| `_fallbackBbox` | 靠 `taskStore.byId(taskId)` 取范围 | 服务图层从服务记录的 `bounds_wgs84` 取;**服务图层没有兜底,取不到就是取不到** |
| `removeByTask` | 任务删除时清图层 | 补 `removeByService(serviceId)`,服务移除时同步清 |

**key 改造的实测影响面(已全仓核实)**:`overlayKey` 除 `overlay.js` 内部一处外,另有 3 处引用,全在 `DataDialog.vue`(`:19` import、`:118` `layerOn()`、`:125` `toggleLayer()`)。**没有任何地方对 key 做字符串解析**(全仓 `split(':')` 零命中),key 只用于 `===` 比较与作 `Map` 键;**无持久化**(`localStorage`/`sessionStorage` 零命中),不需要迁移。所以加前缀是安全的,只要三处一起改。

**范围的完整清单 —— 不要只给矢量补 `bounds_wgs84`**

实测 `core/overlay.py::list_layers()` 产出的 6 种 kind 里,**5 种不带 `bounds_wgs84`**,只有栅格那一种带:

| kind | 有 `bounds_wgs84`? | 现有兜底 |
|---|---|---|
| `tiles`(TMS/OSM 目录、MBTiles) | **无** | 任务 bbox |
| `vector` / `vector_convert` | **无** | 任务 bbox |
| `cog` / `raster_only_bbox` | 有,**但 `crs` 为空或 transform 异常时是 `None`** | 任务 bbox(活路径) |

**瓦片是本工具主产物、叠加最频繁的一类**,而它恰恰没有范围。若按 D5"逐字段对齐"照抄现有结构实现服务 `overlay_desc`,**瓦片服务的定位会同样失效**。因此服务侧必须**为所有 kind 补 `bounds_wgs84`**(来源见 §3.1.1),不只是矢量。

**`overlayable()` 是黑名单,新 kind 会被渲染成可勾选**:`DataDialog.vue:113` 是 `L.kind !== 'preview3d'`。任何新增 kind 都会出现 checkbox,勾选后 `build()` 返回 null,只得到一句泛化的 `MessagePlugin.warning('该图层无法叠加显示')`。本次服务图层的三维/地形项须**复用既有的 `raster_only_bbox` 或 `preview3d` 语义**,不引入新 kind——这样 `build()` 与两份 `KIND_TEXT` 映射表都不用改。

**两处既有缺陷,新增来源会放大(建议本次一并修)**

| 缺陷 | 位置 | 影响 |
|---|---|---|
| **任务队列删除不清图层** | `TaskQueue.vue:163-168` 只调 `taskStore.remove()` + `clearPreview()`,**没调 `overlayStore.removeByTask()`** | 从「任务队列」删任务后,图层留在地图上且无法从任何界面移除——正是 `DataDialog.vue:284` 注释描述的那个 bug,只是发生在另一个入口。**服务图层的 `removeByService` 应同时补上两处调用** |
| **底图 zIndex 与叠加层重叠** | 底图三档是 `[0, 50, 89]`(`utils/basemap.js:30`),叠加层占 10~98 | 图层数达 41 时最大 z 撞底图 50 档,表现为"底图突然盖住成果"且调层序看起来无反应。当前只 1~5 个图层撞不上,加入服务图层后触发概率上升 |

**`LayerPanel.vue` 改动**:底部「＋ 添加图层」改为下拉,两个来源——「从『数据』面板添加」(现有)与「从『服务』列表添加」(新增,复用 `ServiceLayerPicker.vue`)。

**透明度 / 层级 / 定位自动继承,无需额外开发**:

| 能力 | 为何自动可用 |
|---|---|
| 透明度 | `overlayStore.setOpacity()` → `overlays.js::setOverlayOpacity()`,对任意 `ol/layer` 通用 |
| 上下移层 | `overlayStore.moveUp/moveDown` → `applyOrder()` 按数组顺序重排 `zIndex`,与来源无关 |
| 定位 | `zoomToOverlay()` 读 `desc.bounds_wgs84`,服务图层的 `desc` 带上即可;为 NULL 时 `zoomToOverlay` 返回 false,`LayerPanel` 已有的「该图层没有可用的范围信息,无法定位」提示即生效 |

**这是本设计最重要的约束(D5)**:后端 `GET /api/services` 返回的每个服务都带 `overlay_desc`,结构与 `core/overlay.py::list_layers()` 输出逐字段对齐(`kind` / `label` / `url` / `grid` / `flip_y` / `minzoom` / `maxzoom` / `bounds_wgs84`),这样 `overlays.js::build()` 零改动即可渲染服务图层。

**二维地图的能力缺口**:`overlays.js::build()` 支持 `tiles` / `cog` / `vector` / `vector_convert` / `raster_only_bbox`,**不支持 3D Tiles 与地形**。因此:

- 模型 / 地形类服务在**主界面**表现为**范围框 + 「打开三维预览」按钮**(与现有 `preview3d` 的处理一致)。
- 完整三维查看走预览页。

## 7. 已知限制

| 限制 | 说明 |
|---|---|
| 无 token,不做访问限制 | 服务绑 `0.0.0.0` 时局域网可读已开启的服务。默认 `127.0.0.1` 下仅本机 |
| 点要素破例用 Entity | `GroundPrimitive` 无点类型(见 4.3) |
| 无地形时贴地退化为椭球面 | Cesium 固有行为 |
| 主界面不支持三维渲染 | 模型/地形只画范围框 |
| 不自动感知目录变化 | 打开面板时才探活,不做常驻轮询 |
| 范围反算依赖目录完整性 | 瓦片索引反算扫的是文件;20 万文件上限之外只能给估算范围(`bounds_approx=1`) |
| 三种网格不可混用 | 影像 TMS / mercator / Cesium 地形 三套行列定义各不相同,函数签名却相似。用错不报错、只给错范围,靠 §5.1 的回归用例锁住 |
| 地形/模型在主界面不渲染 | `overlays.js::build()` 只认 `tiles`/`cog`/`vector`/`vector_convert`/`raster_only_bbox`,这两类在主界面表现为范围框 + 打开三维预览 |
| 点要素 5000 阈值是经验值 | 单图层点数超过它回退为不贴地 `PointPrimitive`,阈值可调 |
| `GeoJsonPrimitive` 未采用 | cesium 1.143 的新 API,性能优于 Entity 路径,但三个 Buffer 集合不支持贴地。将来做高性能不贴地矢量时是首选 |
| 服务图层与任务图层共用一套 zIndex | 叠加层 z 范围 10~98 与底图三档 `[0,50,89]` 存在重叠区;图层数达 41 时可能撞上底图 50 档。这是既有缺陷,本次仅记录不修 |
| 网格类型可能判错 | 无 `tilemapresource.xml` 且第 1 级行数无法区分时默认 mercator,需手工覆盖 |
| 完全识别不出的数据需手工指定类型 | 既无判据文件、又无数字分层瓦片目录的,扫描会漏,回退到手工注册 |
| 外接盘未挂载会假性失效 | 服务列表会集体显示"源不存在",移除前需确认盘已挂载 |

### 验证过程中发现并修复的问题

单元测试与构建都通过之后，**真实数据与浏览器验证又抓出 7 个问题**——都是"不报错、只是结果错"的类型：

| # | 问题 | 发现方式 | 后果 |
|---|---|---|---|
| 1 | 3D Tiles 的 `box` 是 `root.transform` 下的局部坐标，不是地心 ECEF | 用怀化真实数据跑 | 算出纬度 90° 的无效范围 |
| 2 | 两套网格的多行区间取错纬度边 | 补多行区间测试 | 四至退化成一条线 |
| 3 | 扫描 9.2 万文件超过 120 秒（每层目录各做一次 rglob，与递归叠加成平方级） | 首次真实扫描超时 | 服务面板一打开就卡死 |
| 4 | 同一份瓦片被识别两次（`tms` 与 `tms/3`） | 真实目录扫描 | 候选列表出现重复项 |
| 5 | `preview.js` 独立入口从未装 Pinia | 无头浏览器加载预览页 | `reading '_s'` 运行时崩溃 |
| 6 | 影像服务误用 `TileMapServiceImageryProvider.fromUrl` | 无头浏览器加载服务 | `fromUrl` 对瓦片模板**静默降级**，服务加进来但地图上什么都没有 |
| 7 | 「添加服务图层」按钮与右上角「叠加图层」面板位置冲突 | 无头浏览器点击被拦截 | 按钮点不动 |

第 5~7 条**只有真正打开页面才会暴露**——构建通过、单测通过、类型检查通过都不够。这三条都补了回归测试或位置调整。
