# 全球底图与边缘缓冲(切片包从全球连续放大到局部) — 设计文档

## 1. 问题与目标

### 现状

下载任务只按绘制的 bbox 下载瓦片,导出的切片包因此**只有该范围**:

- 在客户端缩到低层级 / 缩远了,只有一小块有数据,周围是空白
- 选高层级(如只选 z18)时,低层级由 `source_tms_level_plan` 从最高级**降采样**补齐,
  覆盖范围仍然是那个局部范围 —— 降采样只能把图缩小,不能让覆盖范围变大
- 结果:无法从全球视角连续放大到局部;而且一旦叠加了低层级底图,
  就会在范围内/外出现明显的「清晰 vs 模糊」硬边界

### 目标

- 切片包提供**完整金字塔**:低层级全球覆盖,高层级局部细节
- 从全球一路放大到局部最高级,视觉连续
- 每一层在范围外额外外扩 N 圈**原始瓦片**,把「清晰/模糊边界」推远,
  并让边界在各层级之间位置一致(而不是逐层跳变)

### 非目标(本次不做)

- **GeoTIFF 不受影响**:仍只拼「绘制范围 + 最高级」,不因本功能改变
- 不做「高层级全球覆盖」(z6 全球 2048 张、z7 8192 张、z18 天文数字)
- DEM 与本地数据源(`local_dem`/`local_osgb`/`local_pointcloud`)不适用本功能
- 不做「缓冲瓦片单独展示/单独统计」,它们与普通瓦片同源同缓存

### 已确认的取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 入口 | 任务参数里的勾选项 | 不是所有任务都要,不做成全局默认 |
| 作用面 | 只作用于切片包(TMS/OSM) | GeoTIFF 是「范围+最高级」的成果语义,拼全球低层级没有意义且体积失控 |
| 数据源 | 天地图 / Google / Esri 全部支持 | 用户明确要求 |
| 导出格式 | TMS 与 OSM 都做 | 用户明确要求 |
| 注记 | 跟随任务已有的「叠加路网注记」开关 | 不新增独立开关,勾了就一起下 |

### 关键前提(已实测验证,2026-09-30)

| 事实 | 验证方式 | 结论 |
|---|---|---|
| 天地图影像 z1–z5 **全球**有真实数据 | 8 个点(北京/欧洲/美国/南美/非洲/印度/大西洋/太平洋)× z0–z5 实测 | ✓ 全部 200,图像内容与地理位置相符(欧洲出海岸线+雪山,大西洋出纯海面) |
| 天地图注记 z1–z5 全球有数据,**且是中文注记** | 北京/欧洲/美国 × z2–z5 | ✓ z3 欧洲出「挪威/瑞典/芬兰/德国/波兰/俄罗斯」,z5 美国出「美国」+州界 |
| 天地图 `_w` 与 OSM XYZ **同构** | 用 OSM 标准公式算北京 z5 = (x26,y12),直接请求天地图 `_w` 的 (col26,row12) | ✓ 返回渤海湾+华北平原;欧洲那组返回北海+波罗的海 |
| Google 低层级全球有数据 | 六大洲 z5 实测(经代理,重试 3 次) | ✓ 全部成功,7–11KB 真实瓦片 |
| Esri 低层级全球有数据 | 五点 × z2/z3/z5 实测(经代理) | ✓ z5 五点全通 |

> ⚠️ Google/Esri 走代理,实测有**网络抖动**(首次探测约半数 URLError,重试即过)。
> 下载器已有 `max_retries` 重试机制,但全球底图会把瓦片数放大到千级,
> 抖动的影响会被放大 —— 见「7. 待确认事项」。

## 2. 核心设计决策

### D1: 外扩用「每层固定圈数」,不用「固定地理距离」

**这是本设计最核心的一条,推翻了最初的直觉方案。**

客户端在每一层显示的瓦片张数大致固定(约 4×4 张铺满屏幕),因此:

```
第 z 层视野宽度 ≈ 固定张数 × 该层瓦片边长
「每层外扩 N 圈」= 外扩 N / 视野张数 倍的视野宽度 = 相对视野的缓冲比例恒定
```

对比「固定地理距离 L」:z6 视野上千公里时扩 5 公里等于没扩(边界照样紧贴范围边缘);
z18 视野一公里时扩 5 公里又相当于 33 圈,纯浪费。**固定距离是低层级不够用、高层级用不完。**

增量公式(矩形范围 W×H 张,外扩 N 圈):

```
增量 = 2N(W+H) + 4N²
```

| 层级 | 范围相交 | 扩 1 圈 | 扩 2 圈 |
|---|---|---|---|
| z6 | 1 张 | 9 张 | 25 张 |
| z12 | 36 张 | 96 张 | 196 张 |
| z18 | 约 13.4 万张 | +1.1% | +2.2% |

即:即使最大范围的高层级,外扩一圈的代价也只有 **1~2%**。

### D2: 全球底图与边缘缓冲是**同一个机制**

不要写成两套逻辑。两者都是「层级 → 瓦片区间」的推导:

```
第 z 层:
  z ≤ global_max_level  →  该层整层(全球)
  否则                   →  range_for_bbox(bbox, z) 四条边各 ±N 圈,clamp 到层边界
```

低层级的区间恰好铺满整层而已。

### D3: 下载范围**只有一个定义处**

下载、预估、进度、导出四个地方都必须从同一个函数取值。

这条是**从需求 39 的教训来的**:当时预估用一个公式、下载用另一套,导致
「进度显示 100% 但还在下载」。本次的范围推导比当时复杂得多(层级分段 + 外扩 + clamp),
如果再复制几份必然漂移。**新增一个纯函数作为唯一判定处,所有调用方委托给它。**

### D4: 低层级用**原始瓦片**,不用降采样

降采样做不到这件事 —— 它只能把已有的图变小(像素变少),地理覆盖范围一点不变。
范围外的数据**只能靠下载**,没有免费的第二种做法。

用原始瓦片的好处:① 覆盖范围天然是全球;② 画质是数据源原生的,不是重采样出来的;
③ 走同一套瓦片缓存,跨任务复用。

现有 `source_tms_level_plan` 的「兜底金字塔」机制**保留**,用于用户没勾选的中间层级
(见 3.2)。

### D5: 导出分段直映射,Google/Esri 的重投影结果**缓存复用**

| 源 | 网格 | 导出 OSM(3857) | 导出 TMS(geodetic) |
|---|---|---|---|
| 天地图 | geodetic `_c` + mercator `_w` | `_w` 直映射 ✓ | `_c` 直映射 ✓ |
| Google | 仅 mercator | 直映射 ✓ | **需重投影** |
| Esri | 仅 mercator | 直映射 ✓ | **需重投影** |

Google/Esri 的低层级全球瓦片是 3857 的,要变成 geodetic TMS 得转一道。
**全球低层级是固定内容**(与任务范围无关),所以转一次存进缓存、之后所有任务复用,
跟瓦片缓存的道理一样。

转法上**复用现有 `export_tms_from_source`**(把全球低层级拼成一张 3857 图当源),
不新写重投影逻辑。

### D6: 注记跟随任务参数

全球底图段是否下注记,由任务已有的「叠加路网注记」开关决定,**不新增独立开关**。
注记在全球低层级覆盖完整(实测),且是中文注记,对国内用户价值明显。

注记与底图**必须同网格**(现有 `_download_all_grids` 已保证:注记复用底图算出的同一个
`tr`,两者行列号同源)。

## 3. 实现设计

### 3.1 参数模型

`tasks` 表新增两列(走现有 `_MIGRATIONS` 机制):

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `global_max_level` | INTEGER | `0` | 全球底图铺到第几层;**`0` = 不启用**(与现状一致) |
| `buffer_rings` | INTEGER | `3` | 每层范围外外扩几圈;`0` = 不外扩<br>(初版定 1,实测**仍能看到明显边界**,2026-09-30 改为 3) |

用 `global_max_level = 0` 表示关闭,不额外加 bool 字段 —— 少一个可能互相矛盾的字段。

同时要改:`_SCHEMA`、`_MIGRATIONS`、`models` 的读写、`_row_to_dict`。

### 3.2 下载范围推导(核心纯函数)

新增 `backend/core/tile_range.py`:

```python
def level_range(z, grid, bbox, *, global_max_level=0, buffer_rings=0):
    """第 z 层实际要下载/导出的瓦片区间 —— 全局唯一判定处。

    z ≤ global_max_level → 该层整层(全球)
    否则                 → 范围相交区间外扩 buffer_rings 圈,clamp 到层边界
    """
```

- 整层:col ∈ [0, 2^z−1],row ∈ [0, matrix_rows(z)−1]
  (geodetic 行数 `2^(z-1)`,mercator 行数 `2^z`;z=1 时 geodetic 行数为 1)
- 外扩:对 `range_for_bbox` 的结果四边 ±N,再 clamp(避免极地与 ±180° 越界)
- 复用现有 `range_for_bbox` / `mercator_range_for_bbox`,不重写坐标换算

**与「兜底金字塔」的关系**:用户没勾选的中间层级仍由 `source_tms_level_plan` 降采样生成,
它们的**覆盖范围跟随其上方的真实层级**(即同样带缓冲),保证边界不跳变。

### 3.3 下载

改造点集中在 `runner.py::_download_all_grids` 一行:

```python
# 现在
for z in levels:
    tr = range_fn(*bbox, z)

# 改为
for z in levels:
    tr = level_range(z, grid, bbox,
                     global_max_level=..., buffer_rings=...)
```

**额外需要下载的层级**:全球底图要求下载 `1..global_max_level` 这些层级,
即使用户没有勾选它们。下载层级集合 = `用户勾选的层级 ∪ {1..global_max_level}`。

⚠️ 注意:这些层级下的 `local_dem` 等 **DEM 源不适用**(低层级 DEM 无意义),
推导函数要按 provider 类型决定是否启用,并在 `global_max_level=0` 时完全不改变现有行为。

### 3.4 导出 TMS(geodetic)

现有 `export_tms(provider, tile_path_fn, bbox, levels, out_dir, ...)` 是**从缓存瓦片直映射**。

分段调用、写进同一个 `out_dir`(目录结构 `{级号}/{col}/{ty}.png` 天然合并):

| 段 | 来源 |
|---|---|
| 低层级 `1..global_max_level` | 天地图:`_c` 缓存直映射<br>Google/Esri:重投影结果缓存(见 D5)后直映射 |
| 其余层级 | 沿用现有路径(`export_tms` 或 `export_tms_from_source`) |

⚠️ **级号映射是易错点**:输出目录的级号是 `tms_level(z) = z − 1`(gdal2tiles geodetic 约定),
行号是 `tms_row(row, z) = 2^(z−1) − 1 − row`(纵向翻转,因 TMS 行自南向北)。
全球段必须走同一套映射 —— 走错的表现是**瓦片整体错位而不报错**。现有 `export_tms`
已封装这两个换算,全球段复用它、不自己算。

**Google/Esri 的重投影缓存**:新增一个派生缓存,把 mercator 低层级瓦片转成 geodetic 瓦片:

```
{cache_dir}/{provider_key}_geodetic/{z}/{col}_{row}.png
```

- 首次生成:把 mercator 低层级拼成一张 3857 图(全球 z5 = 32×32 张 256px = 8192×8192),
  复用 `export_tms_from_source` 重投影出 geodetic 瓦片
- 之后:命中缓存直接用
- 缓存键带 `_geodetic` 后缀,与原始 mercator 缓存**不互相覆盖**(同 D2 的网格隔离原则)

### 3.5 导出 OSM(3857/XYZ)

现有 `export_osm(src_geotiff, levels, bbox, out_dir, ...)` 是**从 GeoTIFF 重投影** ——
这条路径天生只能覆盖源图范围,所以低层级全球段不能走它。

低层级全球段改为**从缓存直映射**:

| 源 | 低层级来源 | 依据 |
|---|---|---|
| 天地图 | `_w` 缓存瓦片 | 已实测与 OSM XYZ 行列号同构 |
| Google / Esri | 自己的 mercator 缓存瓦片 | 同样构(都是标准 3857 XYZ) |

落在同一个 `{z}/{x}/{y}.png` 目录树里,客户端只加一个图层。
有注记时按现有合成逻辑把注记烘焙进去。

**层级范围**:OSM 输出的层级集合沿用现有规则(最低级 = `min(OSM_MIN_LEVEL, 最高级)`),
**其中 `≤ global_max_level` 的段铺全球**,其余段按 3.2 的范围(范围相交 + N 圈)。
即不改变「输出到哪个层级」的现有行为,只改变各段的**覆盖范围**。

### 3.6 预估与进度

- `core/tile_estimate.py::tile_total` 改为走 3.2 的 `level_range`,不再单独算
- `api/tasks.py` 的 `_estimate_total` / `_estimate_detail` 同样委托过去
- 预估响应里要能区分「范围内」与「全球底图+缓冲」的量,便于前端提示用户
  「这次会多下约 N 张全球瓦片」(否则用户看到总数突然变大不知所因)

### 3.7 前端

`ProcessDialog.vue` 的高级选项区(紧邻「叠加路网注记」):

```
☐ 全球底图 + 边缘缓冲          ← 默认**不勾选**,与现有任务行为一致
    全球底图铺到   z5   [下拉: 关闭 / z3 / z4 / z5 / z6 / z7 / z8]
    边缘缓冲圈数   3 圈 [下拉: 0 / 1 / 2 / 3]
```

- **默认不勾选**:`global_max_level` 默认 `0`,与改动前行为逐字节一致
- 下拉项旁标注该档的全球瓦片量级(z5 ≈ 682 张 / z6 ≈ 2730 / z7 ≈ 10922 / z8 ≈ 43690,
  geodetic 网格),用户自己能看出「铺到 z8」不是一个轻量选择
- 估算区显示「其中全球底图+缓冲约 N 张(跨任务缓存,仅首次需下载)」
- `RedownloadDialog.vue` 同步
- 复用现有估算接口,新增参数透传

## 4. 边界与错误处理

| 情况 | 处理 |
|---|---|
| 用户勾的最高级 ≤ `global_max_level` | 退化为「只下全球」,不重复下载 |
| 缓冲撞到层边界(极地、±180°) | clamp,不越界、不换算出负索引 |
| `global_max_level = 0` | 行为与改动前**逐字节一致**(回归护栏必须覆盖) |
| Google/Esri 代理抖动 | 依赖现有 `max_retries`;若实测失败率高,见「7」 |
| 代理完全不可用 | Google/Esri 的全球底图下载会整体失败 → 明确报错,不静默产出半套金字塔 |
| 缓存体积增长 | 全球瓦片跨任务复用但长期占盘;需要提示与清理入口(见「7」) |
| DEM / 本地数据源 | 推导函数对其禁用全球底图,不改变其现有行为 |

## 5. 测试策略

### 5.1 范围推导(纯函数,重点)

- `global_max_level=0` 时与 `range_for_bbox` 结果**完全一致**(回归)
- 整层区间正确:geodetic z5 = 32×16、mercator z5 = 32×32
- 外扩 N 圈后四条边各多 N,角落符合 `2N(W+H)+4N²`
- clamp:范围贴极地/±180° 时越界被截断
- 两套网格各自用对的行数语义(geodetic `2^(z-1)` vs mercator `2^z`)

### 5.2 下载层级集合

- 用户只勾 z18 + 全球铺到 z5 → 实际下载层级 = {1,2,3,4,5,18}
- 用户勾 z3..z18 → 层级集合不重复

### 5.3 导出合并(行为级)

- TMS:低层级段与高层级段落在同一目录树,`{级号}/{col}/{ty}.png` 不冲突
- OSM:低层级直映射的 (x,y) 与 OSM 标准公式算出的一致(防网格错位 —— 这类错误**不报错**,只是位置全错)

### 5.4 缓存复用

- 第二次任务命中全球瓦片缓存,不重新下载
- `_geodetic` 派生缓存与原始 mercator 缓存互不覆盖

### 5.5 预估一致

- 预估总数 == 实际下载数(需求 39 的同类护栏)

## 7. 待确认事项

1. **代理抖动的影响**:Google/Esri 走代理,实测首次探测约半数 URLError(重试即过)。
   全球底图把瓦片数放大到千级后,失败重试会显著拉长下载时间。需要在实现后实测一轮
   真实下载的失败率,再决定是否要调 `max_retries` 或给这两源单独限速。

2. **缓存清理入口**:全球瓦片是跨任务复用的资产,但也会持续占用磁盘
   (天地图两网格 + 注记约 2728 张,Google/Esri 各约 1364 张)。
   是否需要「清理缓存」界面,以及是否要在任务删除时提示,留待实现后按实际占用决定。

3. ~~**缓冲圈数默认值**~~ **已定(2026-09-30)**:初版 1 圈,实测**仍能看到明显
   边界**,用户拍板改为 **3 圈**(代价约 +5%,可接受)。
