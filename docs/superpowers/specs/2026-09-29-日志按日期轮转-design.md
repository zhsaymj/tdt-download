# 日志按日期轮转 — 设计文档

> 日期:2026-09-29
> 范围:`data/logs/app.log` 的轮转策略改为按日期,并把保留期设为 180 天
> 需求来源:`docs/input/新增需求/需求描述2.md` 的需求35

## 1. 问题与目标

### 现状

`backend/core/logs.py` **已经有**轮转,但是按大小、且从未触发:

```python
fh = RotatingFileHandler(log_dir / "app.log",
                         maxBytes=5 * 1024 * 1024, backupCount=3)
```

实测磁盘状态(2026-09-29):

| 项 | 值 |
|---|---|
| `app.log` 体积 | **3.2 MB** |
| 内容时间跨度 | **2026-07-24 ~ 2026-09-29,共 26 个使用日** |
| 行数 | 32,479 |
| 备份文件(`app.log.1` 等) | **0 个** |

逐日统计(从真实文件量出):

| 指标 | 值 |
|---|---|
| 平均单日 | **100 KB** |
| 最大单日(2026-09-28) | **686 KB**(6,312 行) |
| 5 MB 阈值下最大单日占比 | **13.4%** |

**结论:问题不是"单个文件写太大",而是"一个文件跨了两个月"。** 按大小轮转在当前使用强度下要累积 26 天才转一次,等于没转 —— 这正是需求里"不便于查看"的真实成因。

### 目标

1. 日志**按日期**分文件,单个文件 ≈ 单日日志量(实测 ≤686 KB,平均 100 KB)。
2. 保留 **180 天**,超出自动删除。
3. 前端「运行日志」面板不受轮转影响,始终能看到最新日志。

### 非目标(本次不做)

- **按大小 + 日期双触发**。用户已明确选择纯按日期(标准库 `TimedRotatingFileHandler` 不支持大小上限,双触发需自定义 handler,复杂度不划算)。
- **改动现有那份 `app.log`**。用户选择不动它,让它自然轮转。
- **调整 `_ring` 容量**(800 条)。
- **日志分级落盘 / 按模块分文件**。

### 已确认的取舍

| # | 取舍 | 决定 |
|---|---|---|
| Q1 | 轮转方式 | **按日期**(`when="midnight"`) |
| Q2 | 保留期 | **180 天** |
| Q3 | 现有 `app.log` | **不动**,自然轮转 |
| Q4 | 磁盘代价 | 已接受:典型约 8 MB,最坏约 123 MB(见 §5) |

## 2. 核心设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **用标准库 `TimedRotatingFileHandler`,不自定义** | `when="midnight"` + `backupCount=180` 直接满足需求,零自定义代码。用户已否决双触发方案。 |
| D2 | **多进程轮转的隐患在本项目天然不存在** | `TimedRotatingFileHandler` 在多进程下有已知问题(各进程独立判断轮转时刻)。但本项目的 **worker 子进程不持有文件句柄**:`log_forwarder.install_forwarding` 会 `logger.handlers.clear()` 后换成队列转发,日志统一回主进程落盘(见 `log_forwarder.py` 的模块 docstring)。故只有主进程写文件。**这是选 D1 成立的关键前提**,改动前已核实。 |
| D3 | **`utc` 保持默认 `False`** | 用本机时间,与用户在界面上看到的日志时间戳一致;设 `True` 会让轮转点与文件名日期错开 8 小时。 |
| D4 | **面板与文件彻底解耦,不因轮转改动它的取数方式** | `/api/logs` 读内存环形缓冲 `_ring`,`task.js` 的 WS 分支收实时 `log` 消息 —— 两条来源都不碰文件。**保持现状**即为满足需求,不做任何面板侧改动。 |
| D5 | **加行为级护栏,而非只靠代码审阅** | 用户明确要求"最新日志仍要在面板展示"。仅"读代码确认解耦"不够 —— 加一条测试:**把日志文件改名(模拟轮转)后,面板仍能拿到刚才那条日志**。 |
| D6 | **更新 `LogDrawer` 的提示文案** | 现在写的是"查看**完整**日志 `data/logs/app.log`";轮转后 `app.log` 只是**当天**文件,这句话会变假。 |

## 3. 实现设计

### 3.1 `backend/core/logs.py`(唯一代码改动点)

`import` 改为:

```python
from logging.handlers import TimedRotatingFileHandler
```

`_setup()` 里的 handler 构造改为:

```python
    try:
        log_dir = ROOT / "data" / "logs"
        log_dir.mkdir(parents=True, exist_ok=True)
        # 按日期轮转:每天零点把 app.log 更名为 app.log.<当天日期>,
        # 保留 180 天。原实现是按大小(RotatingFileHandler, 5MB×3),
        # 实测 26 天只用 3.2MB、最大单日 686KB —— 5MB 阈值要 26 天才
        # 轮转一次等于没轮,文件会跨月累积(这正是"不便查看"的成因)。
        fh = TimedRotatingFileHandler(
            log_dir / "app.log",
            when="midnight",
            backupCount=180,
            encoding="utf-8",
        )
        fh.setFormatter(fmt)
        logger.addHandler(fh)
    except OSError:
        pass  # 文件不可写时仅保留内存/控制台
```

> `utc` 不传(默认 `False`,本机时间)。`delay` 不传(默认 `False`,启动即建文件)。

**重启安全性**(标准库行为,验收时实测确认):`TimedRotatingFileHandler` 初始化时用**已存在文件的 mtime** 推算下次轮转时刻 —— 中途重启不会把轮转点算错。

## 4. 边界与错误处理

| 场景 | 行为 |
|---|---|
| 日志目录不可写(打包后权限问题) | 现有 `except OSError: pass` 兜住 —— 只保留内存/控制台出口,面板照常工作(它不依赖文件) |
| 进程跨零点仍在运行 | 下一次写日志时触发轮转(标准库在 `emit` 里检查),不需重启 |
| 进程在零点前后重启 | handler 按文件 mtime 推算,不会漏转或重复转 |
| 超过 180 天的历史文件 | 轮转时顺带删除(标准库 `backupCount` 语义) |
| 现有 `app.log`(跨两月) | 首次轮转时被更名为 `app.log.<轮转日>`。内容跨月但归到一天名下 —— **已确认接受**(Q3) |
| 磁盘空间紧张 | 见 §5 的估算;如需更省可把 `backupCount` 调小,是一处常量 |

## 5. 磁盘占用(180 天的代价,已接受)

| 场景 | 估算 | 依据 |
|---|---|---|
| 典型 | **约 8 MB** | 实测使用频率 42%(26/62 天)× 日均 100KB × 180 天 |
| 最坏 | **约 123 MB** | 假设天天满负荷 × 单日最大 686KB × 180 天 |

> 与现状(一个文件 3.2MB/26 天)相比,长期占用确实上升,换来的是"按天可查 + 单文件小"。

**D2 的前提不需要新测试**:worker 不持有文件句柄这一点,`tests/test_log_forwarder.py`

### 6.2 面板不受影响的行为护栏(D5,本设计的重点)

**不以"断言源码不读文件"实现** —— 那种写法弱。改用行为验证:

```python
def test_recent_logs_survives_file_rotation(self):
    """★ 核心护栏 ★ 日志文件被轮转(改名)后,面板仍能拿到最新日志。

    需求明确要求"不管如何新建文件,最新日志都得在运行日志面板展示"。
    /api/logs 走的是内存环形缓冲而非文件,这条测的就是这个解耦不被破坏。
    """
    from backend.core.logs import logger, recent_logs

    marker = f"轮转护栏-{time.time_ns()}"
    logger.info(marker)
    self.assertIn(marker, [x["msg"] for x in recent_logs(50)])

    # 模拟轮转:把当前文件改名(正是 TimedRotatingFileHandler 的动作)
    log_file = ROOT / "data" / "logs" / "app.log"
    self.assertTrue(log_file.exists(),
                    "前提:文件 handler 已建好 app.log;不存在说明环境不可写,"
                    "该环境无法验证本护栏")
    rotated = log_file.with_name("app.log.1999-01-01")
    shutil.move(str(log_file), str(rotated))
    try:
        # 文件已不在原处,面板仍须能看到刚才那条
        self.assertIn(marker, [x["msg"] for x in recent_logs(50)])
    finally:
        shutil.move(str(rotated), str(log_file))
    # 改名后仍能继续写日志(handler 会按需重建文件)
    logger.info("轮转后继续")
    self.assertTrue(log_file.exists(), "轮转后 handler 应能重建文件")
```

> 测试结束把文件改回原名,避免污染真实日志目录。若 `data/logs/app.log` 不存在
> (目录不可写的环境,如某些 CI),用 `assertTrue` 明确失败并说明前提 —— **不要
> 静默跳过**,否则这条护栏在需要它的地方失效却无人察觉。

### 6.3 手工验证清单

1. 重启服务 → `data/logs/app.log` 仍存在且继续追加(现有文件不被破坏)。
2. 把系统日期/时间调到次日(或用脚本触发一次 `doRollover()`),确认生成 `app.log.<昨日日期>`。
3. 打开前端「运行日志」面板 → 能看到重启后的新日志(实时推送正常)。
4. 面板打开状态下产生日志 → 确认实时追加无卡顿。
5. 确认超过 180 天的文件会被清理(可临时把 `backupCount` 调成 2 验证删除逻辑,验完改回)。
